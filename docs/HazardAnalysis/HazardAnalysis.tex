\section{Introduction}

This document presents the Hazard Analysis for the VR-Based FPV Drone Operator
Training Game. The purpose of the project is to provide users with a virtual
environment where they can learn and practice FPV drone operation before flying
a real drone. The system is intended to support both new users who are learning basic 
FPV controls and more experienced drone operators who want to practice manoeuvres, test 
their skills, or become familiar with different training scenarios in a low-risk environment.

For this project, a hazard is defined as a system condition, failure, or
interaction that could result in harm or loss. This may include physical injury
to the user, damage to equipment, loss of data, system failure, or incorrect
training caused by unrealistic simulator behaviour. Although the system is 
primarily a software simulation, hazards may still arise from the use of VR 
hardware, software failures, inaccurate drone physics, or incorrect user 
interaction with the system.

\section{Scope and Purpose of Hazard Analysis}

\section{System Boundaries and Components}

The system boundary includes the software and hardware directly involved in
running and interacting with the FPV drone training simulator. This includes
the VR headset, input devices, host computer, Unity application, drone
simulation, training functionality, user interface, and locally stored data.
The user and their physical surroundings interact with the system and are
considered when identifying hazards, but they are not components of the
software system itself. Real FPV drones and real-world drone operation are
outside the system boundary.

The system consists of several major software and hardware components. These
components are considered independently during hazard identification because a
failure in one component may affect the safety or correctness of the overall
system.

\subsection{VR Headset}

The VR headset, expected to be a \textbf{Meta Quest 3S}, provides the user's
visual representation of the simulated environment and tracks the position and
orientation of the user's head.

Potential hazards associated with this component include loss of tracking,
visual latency, incorrect orientation, poor headset fit, and the user becoming
unaware of their physical surroundings.

\subsection{Controller Thumbsticks, Triggers, Buttons, and Input Connection}

Controller thumbsticks and triggers provide axis values that are mapped to
drone throttle, pitch, roll, and yaw. Buttons provide discrete commands such as
pause, restart, and respawn. Depending on the final implementation, these
controls may be provided by VR controllers, a game controller, or an external
FPV-style radio controller. The controller connection carries these values and
button events to the application.

Failures may include thumbstick drift, where a centred stick reports an input
and causes unintended drone movement; a stuck thumbstick or trigger,
which maintains a control value after release; or a stuck or unresponsive
button, which repeats or prevents a command. Incorrect axis mappings, inverted
axis directions, or incorrect centre, range, or dead-zone calibration may
produce unintended throttle or steering responses. A disconnected controller,
dropped input updates, or delayed input delivery may cause loss of control,
continued use of a stale control value, or a delayed response to a pilot command.

\subsection{Host Computer}

A computer executes the Unity application and associated simulation software.

Failures may include insufficient hardware performance, overheating, loss of
power, driver issues, or resource exhaustion.

\subsection{Unity Application}

Unity provides the primary execution environment for the game.

This component is responsible for scene management, game logic, user
interaction, rendering, and communication between major software modules.

\subsection{Drone Physics Simulation}

The drone physics subsystem models properties such as:

\begin{itemize}
    \item thrust;
    \item gravity;
    \item acceleration;
    \item angular velocity;
    \item momentum;
    \item collisions; and
    \item drone response to pilot input.
\end{itemize}

Incorrect behaviour in this component represents an important hazard because
users are expected to learn flying behaviour from the simulator.

\subsection{VR Rendering and XR Subsystem}

This subsystem renders the virtual environment and communicates with the VR
headset.

Failures may result in visual artifacts, low frame rate, latency, incorrect
camera movement, or loss of tracking.

\subsection{Training and Scoring System}

The training subsystem may contain tutorials, objectives, checkpoints, scoring
metrics, crash detection, and user performance feedback.

Incorrect scoring or feedback could indicate that unsafe or incorrect flying
behaviour is acceptable.

\subsection{User Interface}

The interface includes menus, settings, warnings, calibration options, pause
controls, and training instructions.

Poor interface design could prevent the user from understanding warnings or
exiting the simulation quickly.

\subsection{Data Storage}

The system may locally store information such as:

\begin{itemize}
    \item user settings;
    \item controller configuration;
    \item training progress;
    \item scores; and
    \item application configuration.
\end{itemize}

Data corruption or unauthorized modification could affect system operation or
training results.

\section{Critical Assumptions}

\begin{enumerate}
    \item \textbf{Stable Internet Connection:} Users have access to a sufficiently stable internet connection for online features, including forms, multiplayer elements, and reviews.\\
    \textbf{Rationale:} Online features require reliable network connectivity to transmit user input, synchronize multiplayer gameplay, and submit or retrieve reviews. This assumption allows the system to be designed around the availability of network connectivity.

    \item \textbf{Honest User Feedback:} Users provide honest gameplay reviews and feedback, and accurately report their experiences with the game.\\
    \textbf{Rationale:} Honest feedback helps ensure that reviews and user evaluations accurately represent gameplay experiences, allowing developers to identify issues and measure goals accurately without accounting for fake comments.

    \item \textbf{Available Storage Capacity:} Users have sufficient available storage space on their systems to install the game and store any locally saved gameplay data.\\
    \textbf{Rationale:} The game requires storage for its installation files, course assets, and locally saved data. Insufficient storage may prevent installation, updates, or the saving of gameplay progress. It may require additional storage after progressing through levels such as save states and leaderboards, this storage should be available for the simulation to use.

    \item \textbf{Basic Gaming Familiarity:} Users have basic familiarity with video games and standard user interface elements, including start screens, settings menus, and navigation controls.\\
    \textbf{Rationale:} This familiarity allows users to navigate the application and access gameplay features without requiring extensive introductory instruction, reducing the complexity of the user interface design.

    \item \textbf{Suitable Hardware Performance:} Users have VR equipment that meets the minimum hardware requirements for running the game.\\
    \textbf{Rationale:} Meeting the minimum hardware requirements helps ensure that the system can maintain acceptable performance, provide a responsive VR experience, and execute the simulation as intended.

    \item \textbf{Accurate Self-Reported Drone Experience:} Users who identify themselves as competent or experienced drone operators accurately represent their level of drone operating experience.\\
    \textbf{Rationale:} The system may rely on users' self-reported experience to understand their familiarity with drone operation and interpret their training results. Assuming these claims are accurate helps ensure that user classifications and performance evaluations are based on their stated level of experience.

\end{enumerate}

\section{Failure Mode and Effect Analysis}

The following Failure Mode and Effect Analysis (FMEA) identifies how each major
component of the system may fail, the effects and causes of each failure, and
the actions taken to mitigate it. Each failure mode is traced to the safety and
security requirements in Section 6 and, where applicable, to the functional
requirements in the SRS. Each row is assigned a hazard reference (H) for
traceability.

The SR column contains two types of identifiers. Identifiers beginning with SR
or NFR followed by a number (e.g., SR5, NFR2) refer to the safety and security
requirements defined in Section 6 of this document. Identifiers containing a
component code (e.g., FR-FLT-04, FR-CHK-02, NFR-SAFE-01) refer to requirements
defined in the FPVR Software Requirements Specification (SRS), a separate
document.

\section{Safety and Security Requirements}

\wss{Newly discovered requirements.  These should also be added to the SRS.  (A
rationale design process how and why to fake it.)}

\subsection{Functional Requirements}

\noindent
\reqdef{SR1} The system shall provide users with a safety notice before their first VR session, reminding them to clear their physical play area of obstacles and remain aware of their surroundings.\\
\textbf{Rationale:} Users may collide with nearby objects while immersed in the virtual environment, potentially causing injury or damaging equipment.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR2} The system shall allow users to pause or exit gameplay at any time during a VR session.\\
\textbf{Rationale:} Users may experience motion sickness, dizziness, or discomfort that requires them to stop playing immediately.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR3} The system shall suspend active gameplay when the VR platform reports a headset disconnection or loss of tracking that prevents reliable interaction.\\
\textbf{Rationale:} Continuing gameplay when tracking is unreliable may cause unexpected interactions and increase user disorientation.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR4} The system shall verify that required VR hardware is detected and initialized before allowing users to begin a flight session.\\
\textbf{Rationale:} Missing or improperly initialized hardware may prevent reliable controller input and compromise gameplay.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR5} The system shall validate controller input values before applying them to the drone simulation and reject values outside supported input ranges.\\
\textbf{Rationale:} Invalid controller inputs may produce unintended drone movements or unpredictable simulation behaviour.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR6} The system shall verify connectivity to required external services before enabling features that depend on them.\\
\textbf{Rationale:} Service connectivity failures may prevent multiplayer sessions or cause dependent features to behave incorrectly.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR9} The system shall validate data received from multiplayer clients before accepting it for gameplay state updates or performance record storage.\\
\textbf{Rationale:} Malformed or manipulated network messages may cause inconsistent multiplayer behaviour or compromise recorded statistics.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR11} The system shall notify users when a network interruption prevents access to multiplayer functionality.\\
\textbf{Rationale:} Users may otherwise be unaware that multiplayer functionality is unavailable or their session has been interrupted.\\
\textbf{Risk:} Low\\[1em]

\noindent
\reqdef{SR12} The system shall disclose what gameplay data is collected, how it is used, and whether it is transmitted to external services before collecting user-associated data.\\
\textbf{Rationale:} Users need to understand how their gameplay information is handled to make informed decisions about their privacy.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR13} The system shall require users to authenticate before accessing personal accounts or user-specific gameplay records, if account functionality is implemented.\\
\textbf{Rationale:} Authentication helps prevent unauthorized users from accessing personal information and saved progress.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR14} The system shall enforce authorization checks before allowing users to view, modify, or delete stored gameplay records.\\
\textbf{Rationale:} Authorization prevents users from accessing or modifying records belonging to other users.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR16} The system shall validate and sanitize user-provided data before processing or storing it.\\
\textbf{Rationale:} Improperly handled input may enable injection attacks, corrupt stored records, or cause unexpected system behaviour.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR18} The system shall terminate or invalidate multiplayer session credentials when a user leaves a session or the session expires.\\
\textbf{Rationale:} Invalidating expired session credentials reduces the risk of unauthorized reuse or continued access to multiplayer sessions.\\
\textbf{Risk:} Medium


\noindent
\reqdef{SR7} The system shall use encrypted communication when transmitting user data or multiplayer session information over a network.\\
\textbf{Rationale:} Unencrypted network traffic may expose user information or session data to unauthorized parties.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR8} The system shall restrict access to stored user-specific gameplay records to the relevant user and authorized system components.\\
\textbf{Rationale:} Unauthorized access may expose private information or allow gameplay records to be modified.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR10} The system shall preserve previously saved gameplay records when unexpected software errors or network interruptions occur.\\
\textbf{Rationale:} Unexpected failures may otherwise result in corrupted records or the loss of user progress.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR15} The system shall securely store authentication credentials and shall not store passwords in plaintext. Passwords shall be protected using an appropriate salted password-hashing algorithm.\\
\textbf{Rationale:} Plaintext passwords may be exposed if stored data is accessed by an unauthorized party.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR17} The system shall prevent unauthorized modification of stored gameplay records and verify data integrity when records are retrieved or updated.\\
\textbf{Rationale:} Tampered performance records may produce inaccurate results and undermine the reliability of user progress tracking.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR19} The system shall limit repeated authentication attempts within a defined period.\\
\textbf{Rationale:} Limiting repeated attempts helps reduce automated password-guessing and brute-force attacks.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR20} The system shall record security-relevant events, including failed authentication attempts and unauthorized access attempts, without unnecessarily logging sensitive user information.\\
\textbf{Rationale:} Security logs support the investigation of suspicious activity while minimizing the exposure of sensitive data.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR21} The system shall display a reminder to take a break after 30 minutes of continuous play.\\
\textbf{Rationale:} Extended VR sessions can cause eye strain, headaches, and fatigue. A 30-minute interval is a common guideline for VR break reminders and gives users a regular opportunity to rest.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR22} The system shall not display visual effects that flash more than three times in any one-second period.\\
\textbf{Rationale:} Rapid flashing can trigger seizures in users with photosensitive epilepsy. The three-flashes-per-second limit follows the WCAG 2.3.1 threshold for flashing content.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{SR23} The system shall inform users that simulator training supports, but does not replace, real-world practice and applicable drone regulations.\\
\textbf{Rationale:} FPVR is designed to build flight skills, but simulated flight cannot reproduce every real-world condition, such as wind, signal loss, and battery limits. Users should continue practising in safe real-world conditions and follow applicable regulations before operating a physical drone.\\
\textbf{Risk:} Medium\\[1em]

\noindent
\reqdef{SR24} The system shall suggest free-flight practice after three consecutive crashes within the same checkpoint section.\\
\textbf{Rationale:} Repeated failures can discourage users and harm their confidence. Suggesting unscored practice gives users a low-pressure way to build skill before retrying the section.\\
\textbf{Risk:} Low

\subsection{Non-Functional Requirements}
\noindent
\reqdef{NFR1} The system shall maintain a frame rate of at least 30 frames per second during standard single-player gameplay on the minimum supported VR hardware.\\
\textbf{Rationale:} Maintaining a consistent frame rate helps reduce visual discomfort and supports an immersive VR experience.\\
\textbf{Risk:} High\\[1em]

\noindent
\reqdef{NFR2} The system shall respond to valid controller inputs within 50 milliseconds under normal operating conditions.\\
\textbf{Rationale:} Low input latency supports precise drone control and provides a more realistic flight simulation experience.\\
\textbf{Risk:} High\\[1em]


\noindent
\reqdef{NFR3} The system shall operate correctly on all VR headsets, controllers, and operating system configurations explicitly listed as supported in the system documentation.\\
\textbf{Rationale:} Defining supported configurations ensures consistent operation and reduces hardware compatibility issues.\\
\textbf{Risk:} Medium\\[1em]


\noindent
\reqdef{NFR4} The system shall restore access to the main menu within 10 seconds of recovering from a recoverable VR tracking or network interruption, provided that the required hardware and services are available.\\
\textbf{Rationale:} Prompt recovery minimizes disruption and reduces the need to restart the application.\\
\textbf{Risk:} Medium


\section{Roadmap}

The following roadmap outlines which of the safety and security requirements
from Section 6 will be implemented within the capstone timeline and which will
be implemented in the future.

\subsection{Requirements Within the Capstone Timeline}

\begin{itemize}
    \item \textbf{\reqref{SR1}:} The system shall provide users with a safety notice before their first VR session.\\
    \textbf{Justification:} Physical injury is the most severe hazard in the system, and a safety notice is simple to implement before any user testing begins.

    \item \textbf{\reqref{SR2}:} The system shall allow users to pause or exit gameplay at any time.\\
    \textbf{Justification:} Users must be able to stop immediately if they feel unwell, so this is required before anyone plays the game.

    \item \textbf{\reqref{SR3}:} The system shall suspend active gameplay when a headset disconnection or loss of tracking is reported.\\
    \textbf{Justification:} Tracking loss can occur in every session, and continuing gameplay without reliable tracking directly causes user disorientation.

    \item \textbf{\reqref{SR4}:} The system shall verify that required VR hardware is initialized before a flight session begins.\\
    \textbf{Justification:} Every flight session depends on working hardware, so this check protects all other gameplay features from the start.

    \item \textbf{\reqref{SR5}:} The system shall validate controller input values before applying them to the drone simulation.\\
    \textbf{Justification:} Controller input drives the core flight simulation, so invalid values must be handled before flight features are built on top of it.

    \item \textbf{\reqref{SR6}:} The system shall verify connectivity to required external services before enabling dependent features.\\
    \textbf{Justification:} Checking connectivity is low effort and prevents features that depend on external services, such as the planned intelligent feedback, from failing without explanation during testing and demonstrations.

    \item \textbf{\reqref{SR10}:} The system shall preserve saved gameplay records during unexpected errors or network interruptions.\\
    \textbf{Justification:} Losing user progress during testing would undermine both the user experience and the evaluation of the system.

    \item \textbf{\reqref{SR12}:} The system shall disclose what gameplay data is collected and how it is used.\\
    \textbf{Justification:} Users must be informed before any data is collected, which includes participants in capstone user testing.

    \item \textbf{\reqref{SR16}:} The system shall validate and sanitize user-provided data before processing or storing it.\\
    \textbf{Justification:} Input validation is a basic safeguard that is far easier to include from the start than to add after data handling is built.

    \item \textbf{\reqref{SR21}:} The system shall display a break reminder after 30 minutes of continuous play.\\
    \textbf{Justification:} Eye strain and fatigue can affect any user, including participants in capstone user testing, and a timed reminder is simple to implement.

    \item \textbf{\reqref{SR22}:} The system shall not display visual effects that flash more than three times per second.\\
    \textbf{Justification:} Seizure risk is a severe hazard, and following the limit while visual effects are created avoids redesigning them later.

    \item \textbf{\reqref{SR23}:} The system shall inform users that simulator training supports, but does not replace, real-world practice and applicable drone regulations.\\
    \textbf{Justification:} The message requires little effort and should be in place before users begin relying on their training results.

    \item \textbf{\reqref{SR24}:} The system shall suggest free-flight practice after three consecutive crashes within the same checkpoint section.\\
    \textbf{Justification:} Free-flight mode is already part of the core system, so suggesting it only requires tracking consecutive crashes.

    \item \textbf{\reqref{NFR1}:} The system shall maintain at least 30 frames per second on the minimum supported VR hardware.\\
    \textbf{Justification:} Low frame rates cause motion sickness, so performance must be maintained throughout development rather than fixed at the end.

    \item \textbf{\reqref{NFR2}:} The system shall respond to valid controller inputs within 50 milliseconds.\\
    \textbf{Justification:} Responsive controls are central to the training experience and affect every flight session.

    \item \textbf{\reqref{NFR3}:} The system shall operate correctly on all explicitly supported hardware configurations.\\
    \textbf{Justification:} Defining supported hardware early focuses testing and prevents compatibility issues from appearing late in development.

    \item \textbf{\reqref{NFR4}:} The system shall restore access to the main menu within 10 seconds of a recoverable interruption.\\
    \textbf{Justification:} Interruptions are expected during normal VR use, and quick recovery avoids forcing users to restart the application.
\end{itemize}

\subsection{Requirements Implemented in the Future}

The following requirements depend on multiplayer functionality, user accounts,
or database storage of gameplay records. These features are stretch goals of
the project that may not be implemented within the capstone timeline, so the
requirements will be implemented when the corresponding features are developed.

\begin{itemize}
    \item \textbf{\reqref{SR7}:} The system shall use encrypted communication when transmitting multiplayer session information.\\
    \textbf{Justification:} Encryption only applies once multiplayer networking is implemented, which is a stretch goal.

    \item \textbf{\reqref{SR8}:} The system shall restrict access to stored user-specific gameplay records.\\
    \textbf{Justification:} Access restrictions only apply once user-specific records are stored, which depends on account functionality.

    \item \textbf{\reqref{SR9}:} The system shall validate data received from multiplayer clients.\\
    \textbf{Justification:} Validation of client data is only needed once multiplayer is implemented, and should be built alongside the multiplayer networking code.

    \item \textbf{\reqref{SR11}:} The system shall notify users when a network interruption prevents multiplayer access.\\
    \textbf{Justification:} This notification only applies to multiplayer features, which are a stretch goal.

    \item \textbf{\reqref{SR13}:} The system shall require users to authenticate before accessing personal accounts or records.\\
    \textbf{Justification:} Authentication is only needed once user accounts exist, which are a stretch goal.

    \item \textbf{\reqref{SR14}:} The system shall enforce authorization checks before stored gameplay records are viewed, modified, or deleted.\\
    \textbf{Justification:} Authorization depends on both authenticated users and stored records, so it follows the implementation of SR13.

    \item \textbf{\reqref{SR15}:} The system shall store passwords using a salted password-hashing algorithm.\\
    \textbf{Justification:} No passwords are stored until account functionality is implemented.

    \item \textbf{\reqref{SR17}:} The system shall prevent unauthorized modification of stored gameplay records and verify their integrity.\\
    \textbf{Justification:} Integrity verification depends on database storage of gameplay records, which is a stretch goal.

    \item \textbf{\reqref{SR18}:} The system shall invalidate multiplayer session credentials when a user leaves or a session expires.\\
    \textbf{Justification:} Session credentials only exist once multiplayer is implemented, and depend on user accounts; both are stretch goals.

    \item \textbf{\reqref{SR19}:} The system shall limit repeated authentication attempts within a defined period.\\
    \textbf{Justification:} Rate limiting only applies once an authentication system exists.

    \item \textbf{\reqref{SR20}:} The system shall record security-relevant events without logging unnecessary sensitive information.\\
    \textbf{Justification:} Most security events relate to authentication and record access, which depend on the user account and database stretch goals.
\end{itemize}

\section*{Vikram -- Reflection}

\begin{enumerate}

    \item \textbf{What went well while writing this deliverable?}

    The team was able to identify potential hazards associated with
    FPVR, our VR drone flight simulation game, and consider how they
    could affect users, gameplay, and system reliability. Examining
    the system component by component helped us identify potential
    failures involving VR hardware, controller inputs, the flight
    simulation, multiplayer functionality, and stored gameplay records.
    Translating these hazards into safety and security requirements
    also helped us define specific system behaviours that could be
    verified through testing.

    \item \textbf{What pain points did you experience during this
    deliverable, and how did you resolve them?}

    One challenge was distinguishing general software defects from
    hazards that could affect user safety, data integrity, or system
    reliability. For example, a VR tracking failure could affect both
    gameplay and user comfort, while a network interruption could
    cause multiplayer issues or lost progress. We addressed these
    challenges by examining the possible causes and consequences of
    each failure and identifying appropriate mitigation strategies.
    Another challenge was determining suitable risk classifications
    and writing requirements that were specific enough to test.
    We addressed this by providing rationales for each requirement
    and identifying system behaviours that could be verified during
    testing.

    \item \textbf{Which of your listed risks had your team thought
    of before this deliverable, and which did you think of while
    doing the Hazard Analysis? For the latter risks, how did they
    come about?}

    Before completing the Hazard Analysis, the team had already
    considered risks related to VR performance, controller
    responsiveness, hardware compatibility, and user discomfort.
    These risks were closely related to the project's objective
    of providing an immersive, responsive, and usable drone
    flight simulation experience.

    The Hazard Analysis encouraged us to examine additional
    scenarios, including loss of VR tracking, invalid controller
    inputs, unexpected hardware disconnections, network
    interruptions, unauthorized access to gameplay records,
    and corruption or loss of saved progress. Some of these
    risks may have been recognized informally earlier, but
    the analysis helped us identify their causes and consequences
    more explicitly.

    These risks emerged by examining each system component
    and considering what could happen if it failed, received
    invalid data, or interacted incorrectly with another
    component. For example, examining controller inputs
    highlighted the possibility of unexpected drone movements.
    Examining multiplayer communication raised concerns about
    manipulated messages and inconsistent gameplay states.
    Finally, examining data storage highlighted the possibility
    of unauthorized access and the loss of saved records.
    This process demonstrated that risks extend beyond the
    simulation itself to include network communication,
    user information, and the reliability of stored data.

    \item \textbf{Other than physical harm, list at least two
    other types of risk in software products. Why are they
    important to consider?}

    Several non-physical risks are relevant to FPVR.

    \textbf{Security and privacy risks:}
    Unauthorized access to accounts or gameplay records could
    expose user information or allow stored results to be
    modified. These risks are important because users need
    to trust that their information is protected and that
    access to personal records is appropriately restricted.

    \textbf{Data integrity and reliability risks:}
    Software errors, unexpected shutdowns, or network
    interruptions could corrupt gameplay records or cause
    users to lose progress. These risks are important because
    training evaluation and performance tracking depend on
    accurate and consistent data.

    \textbf{Performance and usability risks:}
    Low frame rates, delayed controller responses, or confusing
    interactions could reduce immersion and make the simulation
    difficult to use effectively. These risks are especially
    important in VR because responsiveness and consistent
    visual feedback contribute to a comfortable and usable
    experience.

    \textbf{Compatibility risks:}
    Differences between supported headsets, controllers, and
    operating system configurations could cause features to
    fail or behave inconsistently. Considering these risks
    helps the team define supported configurations and plan
    appropriate compatibility tests.

    \textbf{Project and integration risks:}
    Poor coordination, incompatible components, or delays in
    integrating individual contributions could prevent the
    team from completing planned features within the capstone
    timeline. These risks are important because components
    that work independently may still fail when combined
    into the complete application.

    Identifying these risks early allows the team to prioritize
    mitigations, make informed design decisions, and establish
    appropriate tests. Addressing them throughout development
    will help ensure that FPVR is reliable, secure, usable,
    and feasible to deliver within the available time.

\end{enumerate}

    \item \textbf{What went well while writing this deliverable?}

    Organizing the FMEA by system component worked well. Working through the
    flight simulation, VR headset, controllers, checkpoints, scoring, data,
    network, and feedback components one at a time made it much easier to
    brainstorm failure modes than trying to list hazards for the whole system

    without a matching failure mode, or any failure mode without a mitigation,
    stood out right away. Splitting the roadmap into capstone and future work,
    with a justification for each requirement, made our priorities much
    clearer than a single list would have.

    deliverable, and how did you resolve them?}

    The main pain point was deciding which safety and security requirements
    belong in the capstone timeline. Several requirements depend on
    multiplayer, user accounts, or database storage of flight records, which
    are all stretch goals. Rather than removing them,
    I kept them so the hazards are still documented, moved them to the future
    section of the roadmap with a justification for each, and marked the
    related FMEA actions as future work. This keeps the analysis complete
    without committing the team to features that may not be built. Formatting was another pain point: the FMEA table was too
    wide for a portrait page, so I moved it to landscape pages, which then
    required extra work to keep the page numbers and column text readable.

    \item \textbf{Which of your listed risks had your team thought of before
    this deliverable, and which did you think of while doing this
    deliverable? For the latter ones, how did they come about?}

    Before this deliverable, we had already thought about the physical risks
    that are common to VR, such as motion sickness, colliding with objects in
    the room, and losing headset tracking, as well as basic performance risks
    like low frame rates and input latency. While completing the hazard
    analysis, we identified several less obvious risks. Going through each
    component led to gameplay logic failures, such as checkpoints registering
    out of order, unsafe respawn points, and incorrect timers affecting scores.
    Reviewing the hazard analysis checklist, which asks teams to think broadly
    about safety, led to user well-being risks: eye strain from long sessions,
    photosensitive seizures from flashing effects, frustration from repeated
    crashes, and users treating simulator results as readiness to fly a real
    drone. The last risk came from our own SRS, which already states that
    performance in FPVR is not proof of real-world flight ability.

    \item \textbf{Other than the risk of physical harm, list at least two
    other types of risk in software products. Why are they important to
    consider?}

    One type of risk is security and privacy risk, such as unauthorized access
    to user data, intercepted network traffic, or compromised credentials.
    These matter because they can harm users even when the software works
    exactly as intended, and a breach can permanently damage user trust.
    A second type is psychological and well-being risk, such as frustration,
    discouragement, or software that encourages unhealthy amounts of use.
    This is especially important for games and training tools used by the
    general public, since their design directly shapes how users feel and
    behave. A third type is data integrity risk, where results or progress
    are lost or recorded incorrectly. In a training tool like FPVR, inaccurate
    scores or lost progress would give users misleading feedback about their
    skills.
\end{enumerate}
